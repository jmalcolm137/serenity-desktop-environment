# CI (R6/N6)

The suite exists: **88 `scripts/run-*-test.sh` scripts** and a C++ suite in
`test/`, all headless by design. What did not exist was anything that *runs* them
without a human deciding to: `README.md` has said "Headless (CI)" since R1, and
`docs/25-performance.md` enforces a 240 Hz frame budget and a session memory
budget, but nothing enforced either on a change. This is that piece: a driver,
a workflow, and a prebuilt image so the per-push job is minutes rather than hours.

## 1. Cost: why GitHub Actions, and what it actually consumes

Both repositories are **public** (`jmalcolm137/serenity-desktop-environment`,
`jmalcolm137/libgui-wayland`), and use of **standard GitHub-hosted runners on
public repositories is free and unlimited**. That survived the Actions pricing
changes of December 2025 / January 2026, which reduced hosted-runner prices and
introduced a cloud-platform charge for *private* repositories and self-hosted
runners; public-repo standard runners were explicitly left free.

| | Standard Linux runner |
|---|---|
| Public repo | **free, unlimited** |
| Private repo, GitHub Free | 2,000 min/month, 500 MB artifacts, 10 GB cache/repo; Linux is a 1× multiplier |
| Larger runners | **always billed, even on public repos**; never use `-4-core` |

Self-hosted runners stay free on public repositories (the announced billing
change for them was postponed), which matters for §3: a runner on the development
machine would inherit the 1.2 GB build tree and run the whole suite in minutes.

### 1.1 Nightly: what it costs, and what to keep an eye on

Nightly is affordable *because* the repositories are public: the three jobs
(`smoke`, `full`, `budgets`) plus the weekly image rebuild all run on standard
GitHub-hosted Linux runners, which are free and unmetered there. Nothing about
the schedule needs a paid plan.

The resources that are actually finite, none of which the schedule stresses:

| Resource | Free allowance | What we use |
|---|---|---|
| Runner minutes | unlimited (public repo) | ~3 job-hours per night, ~2 image-hours per week |
| Actions cache | 10 GB per repository | deliberately near zero: the framework lives in the image, not a cache (the SDE build is 61 MB, cached only if we choose to) |
| Artifact storage | 500 MB (shared with Packages) | a few MB of logs, uploaded only on failure, default 90-day retention |
| Runner disk | ~14 GB | image layers + the SDE build (~2–3 GB) |
| Concurrent jobs | plan-dependent | 3 nightly jobs; irrelevant |

Two things to watch as the suite grows: the `full` job's wall-clock (180-minute
timeout today) and artifact retention, since a repeatedly-failing job uploads
logs every night.

## 2. The binding constraint is the build, not the minutes

Measured in the development checkout:

| Piece | Size | Notes |
|---|---|---|
| SerenityOS checkout | 205 MB | `libgui-wayland/scripts/fetch-serenity.sh`: blobless, sparse, **pinned** (`80baeb29…`): reproducible and much smaller than a full clone |
| wlroots (vendored source) | 31 MB | `third_party/wlroots`, meson build |
| **Lagom framework build** | **1.2 GB** | LibGfx/LibGUI/LibWM + tools |
| SDE build | 61 MB | compositor, services, applets, apps, tests |

Dependencies + wlroots + Lagom + SDE, cold, is realistically **1–2.5 hours on a
4-vCPU runner**. Free minutes make that possible; it does not make it useful to do
on every push. Two mechanisms, in order of preference:

1. **A prebuilt image on ghcr.io** (`ci/Containerfile`): distro deps, wlroots, and
   the Lagom framework baked in, keyed on the SerenityOS pin. Jobs then build only
   the SDE and run tests. Public images are free.
2. **Actions cache** (10 GB per repo on Free): cache the framework build keyed on
   the SerenityOS pin. The framework does *not* depend on the test matrix (only
   the 61 MB SDE build does), so one cache entry serves every configuration.

`ENABLE_LAGOM_CCACHE` is currently `OFF`; turning it on with a capped cache helps
the first build either way.

## 3. Toolchain

The port builds `-std=c++26`; the development machine has **GCC 16.2.1** and
**CMake 4.4.4**. A current Ubuntu LTS default toolchain will not do, so the image
is **Arch-based** (`archlinux:base-devel`), which also matches the packaging
target in [`13`](13-native-session-and-aur-packaging.md) and always carries a
current GCC/CMake. Jobs run *inside* that image
(`jobs.<id>.container.image`), so `ubuntu-latest` is only the VM host.

## 4. What runs where

| Job | Trigger | Runs | Target |
|---|---|---|---|
| `smoke` | push, pull request | `build-full-sde.sh --with-apps`, then `run-all-tests.sh --tier fast` | < 75 min |
| `full` | nightly, `workflow_dispatch` | `run-all-tests.sh --tier full` (everything) | < 90 min |
| `budgets` | nightly (non-blocking at first) | `run-perf-test.sh`, `run-session-memory-test.sh` | visible, not gating |

The `smoke` job builds the applications too. The image deliberately does not carry
them, and a third of the fast tier runs them (CrashReporter, Debugger, TextEditor,
SystemMonitor, the applets), so without `--with-apps` those tests can only fail. The
target above is the job's own timeout (75 min), not a measurement: the tier cost
~21 min before the applications were built, and the extra compile has not yet been
measured on a runner.

Failures upload each test's log as an artifact. `budgets` is non-blocking on
purpose: the 240 Hz p99 assertion and the PSS limits are machine-sensitive, and a
shared runner will flake them. The `SDE_PERF_*` / `SDE_SESSION_*_LIMIT_KB` knobs
exist so CI can express a looser gate without weakening the local budget; once a
runner baseline is measured, tighten them and make the job blocking.

## 5. What cannot run on a hosted runner

- **`run-profiler-test.sh`**: needs `perf_event_open`, which the runner's
  container blocks (`perf_event_paranoid`). It must **SKIP** with a reason rather
  than fail. Tracked in the tier list until the test detects it itself.
- **Host services**: NetworkManager, a PipeWire daemon, a portal frontend, a
  camera. Those tests are `full` tier and must skip cleanly when the service is
  absent; the per-push gate must never depend on one.
- **No `/dev/dri`.** Fine: the suite is headless by design, and Xwayland binds its
  own socket under the test's runtime directory.
- **DRM/KMS, libinput, real GPU, input→photon latency**: the R6 items in
  [`08-compositor-gaps.md`](08-compositor-gaps.md), not coverable in CI.

## 6. Hermeticity, and an incident worth reading

Two things stop a test run from being hermetic, and both bit on day one. The
suite is only safe to run on a working machine *because* of what follows.

### 6.1 The session's services answer for the test's (`SDE_SESSION_DIR`)

`LibWM` **defers** to a process already listening on the session's portal path, so
a test run on a machine with a live session can be answered by *that* session's
services instead of the compositor the test started. This is the failure mode
that made `run-audio-test.sh` red until it isolated itself, and it made
`run-setting-test.sh` red for the same reason.

`run-all-tests.sh` now gives **every** test a private `SDE_SESSION_DIR`, which
fixed `run-setting-test.sh` and makes the suite hermetic in CI as well. Tests that
want their own path still set it and win.

### 6.2 Xwayland shares the machine, and the compositor did not survive it

**What happened.** The first full local run, on the machine hosting the live
session this was written on, killed that session. The compositor crashed with:

```
SIGSEGV
  libwlroots: wlr_xwayland_set_workareas+0x11c
  WindowServer: update_xwayland_workareas   ← arrange_layers ← layer_surface_commit
```

**Why.** An X server's sockets are **abstract** (`@/tmp/.X11-unix/X<n>`) and are
therefore shared with every other X server on the machine; no filesystem
namespace separates them. Each test compositor enabled Xwayland, and Xwayland's
display selection is a race over a global namespace: the session's X server was
on `:1` and a test's took `:1` too. The session's X server died; the compositor's
`xwayland_started` flag only recorded that it had been ready *once*, so the next
layer-surface commit called `wlr_xwayland_set_workareas()` on a dead Xwayland,
which dereferences the XWM connection wlroots had since dropped → SIGSEGV → the
session's supervisor restarted it.

**Two fixes, one product and one process.**

1. **The compositor survives a dead Xwayland.** `update_xwayland_workareas()`
   now checks `wlr_xwayland_get_xwm_connection()` before asking wlroots to report
   the workarea. Any X server going away, for any reason, in any deployment,
   can no longer take the compositor with it. This is the real bug; the test run
   only found it.
2. **A test's X server cannot be seen by the session's.** `run-all-tests.sh`
   exports `SDE_XWAYLAND=0`, so no test compositor starts an X server unless its
   test asks for one. The five tests that *do* exercise X11 re-exec themselves in
   `unshare -Urnm`: a **network** namespace (abstract sockets are namespaced
   there, not by the filesystem) plus a mount namespace carrying a private,
   correctly-owned `/tmp/.X11-unix` (Xwayland refuses one it does not own, and
   the host's is owned by root, which is an unmapped uid inside a user
   namespace). Where unprivileged namespaces are unavailable (some containers)
   they fall back to skipping while a session owns the display.

   Verified with a session live: the tests pass, the session's socket table is
   byte-for-byte unchanged during the run, and the session's compositor pid never
   moves.

### 6.3 The session's watchdog watched the tests' heartbeat

The same inheritance, one level deeper, with worse consequences. A session's
liveness file was **machine-global** by default (`$XDG_RUNTIME_DIR/sde-heartbeat`),
and the supervisor exports it, so every process the session starts carries it,
including the shell this driver is launched from. A test compositor therefore
wrote the *live* supervisor's liveness file, and a test that runs a supervisor
(the watchdog's own tests do, deliberately) removed it. The live watchdog saw its
heartbeat go stale and restarted the live compositor, killing every client in the
session. One local suite run did that three times; the supervisor's log records
ten `compositor heartbeat stale … restarting` lines.

Two fixes. The heartbeat default is now **per session**
(`sde-heartbeat-$SDE_SESSION_DISPLAY`), so a session, a seat, and anything that
inherits the environment cannot collide. And the driver gives every test its own
`SDE_HEARTBEAT_FILE`, after clearing the session-level variables it inherited
(`SDE_SESSION_*`, `SDE_HEARTBEAT_FILE`, `SDE_WM_PORTAL_PATH`, `SDE_STATE_DIR`,
`SDE_SESSION_LOG`) so a test can never reach the session's files, sockets or
services.

### 6.4 The guard that should have existed first

`run-all-tests.sh` now **refuses to run** when it detects a live session (the
session's compositor socket, or a heartbeat written within the last minute),
because these tests drive session-level state (the watchdog, input capture, the
lock) and cannot be made unconditionally safe on a machine someone is using. It
exits with status 3 and says why; `SDE_ALLOW_LIVE_SESSION=1` overrides it, at the
operator's own risk. CI has no session, so the guard never fires there, and the
rest of the suite's hermeticity work (§6.1–6.3) is what makes it safe there.

Every rule in this section has the same shape, and it is worth stating plainly:
**a test may only touch state it created.** The two failures above were both a
test touching the session's state because it inherited a path the session had
exported.

### 6.5 Coverage: tiers decide *when*, not *whether*

No test is excluded from CI. 83 run on every push; the 5 X11 tests
(`xwayland`, `xwayland-exit`, `taskbar-grouping`, `active-window`, `selection`)
run in the nightly `full` job and, thanks to §6.2, locally too, which they never
were safely before. Swapping the other 83 to Xwayland-off removes no assertion:
nothing outside those 5 asserts anything about X, so the X server they used to
start was incidental, and it was what made runs non-hermetic.

One open finding, recorded rather than hidden: `run-taskbar-grouping-test.sh`
fails its **X11 `WM_CLASS`** assertion: the compositor logs
`X11 window 0 class='' instance=''` for an `xterm`, so the grouping input is
empty. That is not a namespace artefact (the X client and the compositor are in
the same namespace and the native checks all pass); it looks like a real gap in
how X11 windows reach the group logic.

### 6.6 The image that could not configure: one line, added twice

The image build failed in 1m17s, in its *first* CMake configure, while every local
build passed. The error named a directory rather than a file:

```
The binary directory .../build/lagom/libeglgpu is already used to build a source
directory. It cannot be used to build source directory .../libeglgpu
```

Two patches added the same line:

```
add_subdirectory("${SERENITY_PROJECT_ROOT}/../libeglgpu" "${CMAKE_CURRENT_BINARY_DIR}/libeglgpu")
```

`0001-lagom-build-full-libgui.patch` and `0007-libeglgpu-mesa-backend.patch`. On a
development tree the loop classifies one of them "already applied" and the duplicate
never appears, so the local build (and its `build/lagom`) was configured long before
the second copy existed. The image applies the whole patch set to a **fresh**
SerenityOS clone, both apply, Lagom gets two `add_subdirectory()` calls for one
binary directory, and configure dies.

The lesson is worth more than the fix: *"the local build passes"* proves nothing
about the patch set. Replay it against the pinned revision in a scratch tree before
trusting it, which is cheap and needs only the pristine file:

```sh
mkdir -p /tmp/sim/Meta/Lagom
git -C serenity show HEAD:Meta/Lagom/CMakeLists.txt > /tmp/sim/Meta/Lagom/CMakeLists.txt
cd /tmp/sim
for p in <port>/*.patch <sde>/*.patch; do
    git apply --recount -C1 --include='Meta/Lagom/CMakeLists.txt' "$p"
done
```

### 6.7 Four ways a green local build hid a red CI build

Everything below compiled and passed on a development machine, and failed in CI. They
are worth listing together because each one cost a full round trip.

1. **A build directory older than the change.** The image applies the patch set to a
   *fresh* clone; a development `build/lagom` was configured before a patch existed.
   A duplicate `add_subdirectory()` (the EGLGPU one) and a dangling `StringView` both
   compiled here and not there.
2. **A working tree that had drifted from what the patch set reproduces.** `0052`
   treated a guarding `#if` as *context*, so a fresh clone got the `#endif` without
   the `#if`; the tree had it because it was there when the patch was generated.
   The same drift hid a *missing* patch: `CodeComprehension` was added to Lagom's
   `lagom_standard_libraries` list in the working tree and never captured, so every
   local build could link HackStudio's language server and CI could not
   (`cannot find -lLibCodeComprehension`). Note which side is wrong: here the tree
   was, not CI.
   The check for both of these is cheap and is now how patch changes are verified:
   replay the set against the pinned revision in a scratch tree
   (`git show HEAD:<file>` + `git apply`), and diff against the working tree. A diff
   here is either a missing patch or a stray edit, never nothing.
3. **A run-wide default versus a test whose purpose is to control it.** Exporting
   `SDE_BACKENDS=headless` for the whole run stopped the multiseat preflight check
   from exercising the refusal it exists to test (it hung until the driver killed it)
   and made the layer test's output-name expectation wrong. A scoped change belongs
   in the tests that need it; a default is for the tests that need *it*.
4. **Output thrown away.** `build-full-sde.sh` ran each step with its output to
   `/dev/null`, so a failing step produced a line and an exit code and nothing at
   all. It now keeps the output and prints it on failure, and the first run after that
   named the `#endif` in one line.

Two more that are not about builds:

* **The session exports `SERENITY_RES_ROOT`** (and much else) to everything it runs,
  so a development shell supplies environment CI does not. About fifteen tests were
  aborting in `MUST(try_load_from_uri())` (a font the client could not find) for
  exactly this reason. Suspect this first when a test passes here and fails there.
* **A stale log expectation is a test bug with a confusing face.** Three tests
  (`output`, `settings`, `headless`) grep for log lines the compositor stopped
  writing when the output code was reworked. The behaviour they meant to check was
  intact and asserted elsewhere; the *text* was stale.

### 6.8 The failures the first real runs surfaced

Once the workflow was running it stopped being a question of whether the suite
passed and became a question of *which* job was red and why — a run reports a test
name and, on failure, its log, but not which of the several things that could make
that test fail did. The first runs put the fast tier at 80/2, the full suite at
89/7 and the budget job at its own failure.

The method that settled them is worth recording, because it turned hours of
push-and-wait into minutes: **pull the CI image and reproduce inside it**, with the
driver and the same container the job uses.

```sh
podman pull ghcr.io/jmalcolm137/sde-ci:latest
git clone . /tmp/ci-work                                  # a clean tree, like the job
podman run -d --name repro --network=host -v /tmp/ci-work:/work:Z -w /work \
    ghcr.io/jmalcolm137/sde-ci:latest sleep infinity
podman exec repro bash -c 'scripts/build-full-sde.sh --with-apps'
podman exec repro bash -c 'scripts/run-all-tests.sh --tier full --only run-<test>'  # note --tier
```

`--only` still applies the tier filter, so a `full`-tier test needs `--tier full
--only …` or it reports "no tests selected". The image carries the pinned framework
and a built SDE, so only the reproducer needs to run.

Seven things it found. Two are the product; the rest are the tests and the harness.

1. **The output scale was never applied to a fresh output.** `server_new_output()`'s
   no-saved-entry path (`no screenlayout.ini entry`: a virtual output, which is
   *every* CI run) committed a mode and left the scale at 1x; `SDE_OUTPUT_SCALE` /
   `[Output] DefaultScale` only took effect on a later `apply_output_scale()` tick.
   `run-hidpi-fidelity-test.sh` dumps at 1x and 2x and asserts 2x is the 1x dump
   doubled; it got `640x400, not twice 640x400` — the same dump twice, which is the
   test doing its job. The fix is one `wlr_output_state_set_scale()` on that path.
   The saved-layout path had it; only the no-entry path had lost it in the rework
   that collapsed the two (`e47ddc1`).
2. **A session's state file was truncated in place.** `save_states()` rewrote
   `sessions/<id>` on *every* geometry change with `O_TRUNC`; a compositor stopped
   between the truncate and the write left a 0-byte file, and
   `run-session-management-test.sh` then lost its session after the restore step had
   already succeeded (the CI failure read "MISSING: session state file"). It now
   writes a `.tmp` and renames it over the state, so the file is always a whole
   state. The window is small, but this runs on every move — a kill or a crash is
   enough to hit it.
3. **A click on the Taskbar raced the pointer hotplug.** A headless seat has no
   input devices until `virtual-input-test` creates them, so the Taskbar binds its
   `wl_pointer` only once that capability arrives. A test that clicks the start
   button in the same breath sends the press before the bind and the release after
   it; the compositor drops the press — the client has no pointer resource yet —
   and the log shows `mouse up window … button=1` with no `mouse down`. On a runner
   `run-fragile-window-test.sh` and `run-menu-dismiss-test.sh` were ~6/10. Both now
   plug a pointer in over the button and wait for `pointer entered window` before
   clicking; 10/10 each under load. The signature is worth remembering: *a release
   with no matching press is a client that bound its pointer late, not a lost input
   event.*
4. **The Xwayland test sampled an animated state.** A workspace switch slides the
   stacks for 200 ms and the hide lands when the transition *finishes* — after the
   `switched to workspace 0,1` line the test keyed off. It grepped the instant the
   switch was logged and lost the race; `run-xwayland-test.sh` now bounded-waits for
   the `visible=false` line like the rest of the suite waits for what it asserts.
5. **The session-memory test had no runtime directory of its own.**
   `run-perf-test.sh` creates its own `XDG_RUNTIME_DIR` and says why: a container is
   not a login session, `XDG_RUNTIME_DIR` is unset and `/run/user/<uid>` may not
   exist, so the compositor cannot create its Wayland socket at all
   (`failed to create a Wayland socket`) and the desktop never comes up.
   `run-session-memory-test.sh` did not, and the `budgets` job runs both scripts
   *directly* rather than through the driver — which is what gives every other test
   its private runtime directory — so it could only fail there.
6. **The image must move when the framework pin does.** `run-wallpaper-resource-test.sh`
   wants `blue-grid.png`, which the pinned SerenityOS tree does not carry;
   libgui-wayland `0066` supplies it. The image in use was built from a port commit
   before `0066`, so the asset was absent and the compositor logged
   `could not load the seed wallpaper`. Nothing in the SDE can fix that — a test may
   legitimately depend on framework *content*, and the image is what carries it —
   so the fix is to rebuild the image whenever the framework revision moves
   (rebuilding it by hand for the diagnosis confirmed the test itself is correct:
   with the asset present it passes). This is the same shape as §6.6: *"the local
   build passes" is not a statement about a fresh clone or an older image.*
7. **The `budgets` job built the SDE without the applications.** Its session-memory
   test measures the desktop — `FileManager -d`, which is an *application*, not part
   of the base build — and includes it in the per-client budgets. Built without
   `--with-apps` the binary is simply absent, `FileManager -d` never starts, and the
   wait times out as `the desktop never came up`, which reads like a compositor
   fault. The job now builds `--with-apps` (as `smoke` already did), and the test
   checks for the binary first and names it, so the same mistake cannot masquerade as
   a compositor failure again. The local reproducer had hidden this: the `--with-apps`
   build for the smoke tier had already populated the same `build/lagom/bin` the test
   looks in, so the script passed here and failed there. That is §6.7's lesson one
   more time — *a green local run is not a statement about the job's tree.*

The workflow files were also carrying the **Node 20 deprecation** — every run warned
that `actions/checkout@v4` and `actions/upload-artifact@v4` were being forced onto
Node 24. They are bumped to the current majors (`checkout@v7`,
`upload-artifact@v7`, `docker/login-action@v4`, `docker/setup-buildx-action@v4`,
`docker/build-push-action@v7`).

With all seven on the image's own tree the fast tier is **82 passed, 0 failed,
4 skipped**, the full suite is **97 passed, 0 failed, 4 skipped** (the four skips are
the hardware-dependent ones from §5), and both budget scripts pass — the frame and
latency budget and the session-memory budget. On the runner the smoke job and the
full suite are green; `budgets` is `continue-on-error` (§4), so its failures report
without failing the run.

## 7. The driver

```sh
scripts/run-all-tests.sh                     # the per-push tier
scripts/run-all-tests.sh --tier full         # everything
scripts/run-all-tests.sh --only 'run-*portal*' --timeout 600
scripts/run-all-tests.sh --list              # the selection, with tiers
```

It discovers `scripts/run-*-test.sh`, runs each with a timeout, records how long
it took, recognises `SKIP:` output, and prints a summary with the slowest tests
and the tail of each failure. Exit status is non-zero if anything failed or timed
out. Tiers come from a marker in the test's header:

```sh
# ci-tier: full
```

Unmarked tests are `fast`. Marking is **evidence-based**: the durations the driver
prints are what put a test in a tier, and `# ci-tier: full` is for tests that are
heavy, timing-sensitive, or need something a runner lacks. A test that cannot run
here should print `SKIP: <reason>` and exit 0; the driver reports it as skipped,
not failed.

Safety: the driver never signals anything but the test it started. Each test owns
its isolation (its own `setsid` process group and runtime directory) and its
`trap … EXIT` cleanup runs when a timeout sends it SIGTERM, so a timed-out test
still takes its compositor down with it. Nothing matches processes by name or
command line; see the incident note in [`25-performance.md`](25-performance.md).

### Tiers, from the first measured run

Two partial runs of the whole suite produced durations for **40 of the 88** tests
before each was stopped: the first because the Xwayland tests killed the host
session, the second by hand after the watchdog restarted it. That is enough to set
tiers on evidence rather than taste:

| | measured | sum |
|---|---|---|
| whole suite | 40 tests | 700 s (11.7 min) |
| fast tier | 29 of 73 | 162 s (2.7 min) |

The slow tests are slow *by design* (they wait: idle 51 s, cursor highlight 58 s,
launch animation 57 s, edge snap 57 s) or heavy: they build and launch the
application set (apps smoke 41 s, demos 61 s, games 57 s, DevTools 18 s). Those
nine, plus the input-capture portal test (93 s, and portal-dependent), are `full`:

```
run-apps-smoke  run-demos  run-games  run-devtools  run-input-capture-portal
run-cursor-highlight  run-launch-animation  run-edge-snap  run-idle  run-icon-reload
```

The split is **73 fast / 15 full** (the five X11 tests were already nightly). The
fast tier is 2.7 min of measured tests; the 44 it has not measured yet should put
it near 10 min locally, inside the 45-minute job timeout on a slower runner.
**Nothing is excluded**: `--tier full` is still the whole suite, and that is what
the nightly job runs.

### Two failures the runs recorded, both left honest

- **`run-devtools-test.sh`: SQLStudio faults**: in both runs, while the other
  three DevTools map their windows. SQLStudio is the one DevTools app with a
  *service* dependency (the ported SQLServer), so the likely cause is that nothing
  starts it. Open: it needs the app's own output, which the test does not capture.
- **`run-launch-exec-test.sh`: "the executable did not run"**: a regression this
  work introduced. The driver exported `SDE_SESSION_DISPLAY=sde-tests`, which was
  never needed (isolation comes from `SDE_SESSION_DIR`) and changes the session
  name the launch path derives. Removed; tests now run in the configuration they
  were written for.

### One failure the runs still record: an intermittent shim crash

`run-setting-test.sh` failed one nightly run in 1 s, and passed the run before it
and every run after. The payload is `libwm-setting-test`, which sets the mouse
acceleration and double-click speed through the app-facing WindowServer protocol and
reads them back; the test already anticipates the shape of this failure (the comment
at its head) because a crash after applying leaves an empty app log. The log from
the artifact:

```
run-setting-test.sh: line 47: 19517 Segmentation fault (core dumped) …
  MISSING: the payload exited cleanly                    (exit 139)
  MISSING: the shim answered the new value
  MISSING: the shim answered the new double-click speed
  ok: the compositor received the setting
  ok: the compositor persisted it in input.ini
```

So the **compositor did its half** — `host setting mouse.acceleration=2.5` and
`mouse.double_click_speed=321` are in the compositor log and in `input.ini` — and the
shim, which had connected and read the host settings, then segfaulted before it
answered. It is a crash in **`libgui-wayland`'s** setting round-trip, not in this
repository, and it is rare: twelve consecutive runs inside the CI image did not
reproduce it, and the same test passed in the full suite an hour earlier. What made
it visible at all is that the payload's status is now checked separately from the
shim's answer (`APP_STATUS`, the "payload exited cleanly" assertion) — without that
the crash would have been reported as *the shim answering the wrong value*, which is
a different bug in a different file.

Left open and recorded rather than hidden: it needs the shim's own frame of the
crash, which means catching it under a debugger (or running the suite in a loop until
it trips). It is on the `docs/24` boundary, so the fix belongs on that side.

### And a second: the Alt release never reached the client

Re-running the full job failed a *different* test, so this is the suite and not one
test's problem. `run-input-test.sh` (fast tier) failed one run with:

```
MISSING: Alt release after Alt+Tab (client saw 0 key events)
```

The compositor's half was done — `WindowSwitcher: activating wm_id=1` is in its log,
and the menu, tiling, snap, workspace and both switcher checks passed — so the keys
reached the compositor and the client received *none*. The same test passed the smoke
job and the full suite earlier the same evening, and the guard that made it legible
is the "client saw N key events" count, which the driver gained in `af1e522` for
exactly this.

The leading explanation is visible in the compositor log, which shows a device per
step:

```
WindowServer: virtual pointer connected
WindowServer: virtual keyboard connected     ← once per virtual-input-test invocation
```

`virtual-input-test` runs once per step and each invocation *creates and then
destroys* its virtual pointer and keyboard. Between two invocations the seat has no
keyboard, so the client rebinds it; a key that lands in that window goes to nobody.
Steps that gather their keys while the device is up pass; the one that samples the gap
fails. That is why it is rare and why it moves between tests and between runs.

Two ways out, both open: hold *one* input session across a whole sequence (the tool
already sequences operations with `--sleep`, so this is a test change and the smaller
one), or keep the seat's keyboard stable across virtual-device churn (a product
decision — real hardware does not churn, which is why only the tests see it).

## 8. Deliberately not covered

- **Real hardware** (DRM/KMS, libinput, multi-GPU, colour, direct scanout): R6's
  remaining items need a machine, not a runner.
- **Accessibility (R5)** and the wlroots-gated Xwayland items.
- **A per-renderer matrix.** `SDE_PERF_RENDERER=auto` and `SDE_RENDERER=gles2` are
  runnable headless, but GL on a runner means llvmpipe; the matrix is worth adding
  only once the image carries a GL stack.
