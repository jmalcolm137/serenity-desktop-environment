# CI (R6/N6)

The suite exists: **88 `scripts/run-*-test.sh` scripts** and a C++ suite in
`test/`, all headless by design. What did not exist was anything that *runs* them
without a human deciding to — `README.md` has said "Headless (CI)" since R1, and
`docs/25-performance.md` enforces a 240 Hz frame budget and a session memory
budget, but nothing enforced either on a change. This is that piece: a driver,
a workflow, and a prebuilt image so the per-push job is minutes rather than hours.

## 1. Cost: why GitHub Actions, and what it actually consumes

Both repositories are **public** (`jmalcolm137/serenity-desktop-environment`,
`jmalcolm137/libgui-wayland`), and use of **standard GitHub-hosted runners on
public repositories is free and unlimited**. That survived the Actions pricing
changes of December 2025 / January 2026, which reduced hosted-runner prices and
introduced a cloud-platform charge for *private* repositories and self-hosted
runners — public-repo standard runners were explicitly left free.

| | Standard Linux runner |
|---|---|
| Public repo | **free, unlimited** |
| Private repo, GitHub Free | 2,000 min/month, 500 MB artifacts, 10 GB cache/repo; Linux is a 1× multiplier |
| Larger runners | **always billed, even on public repos** — never use `-4-core` |

Self-hosted runners stay free on public repositories (the announced billing
change for them was postponed), which matters for §3: a runner on the development
machine would inherit the 1.2 GB build tree and run the whole suite in minutes.

### 1.1 Nightly: what it costs, and what to keep an eye on

Nightly is affordable *because* the repositories are public: the three jobs
(`smoke`, `full`, `budgets`) plus the weekly image rebuild all run on standard
GitHub-hosted Linux runners, which are free and unmetered there. Nothing about
the schedule needs a paid plan.

The resources that are actually finite, none of which the schedule stresses:

| Resource | Free allowance | What we use |
|---|---|---|
| Runner minutes | unlimited (public repo) | ~3 job-hours per night, ~2 image-hours per week |
| Actions cache | 10 GB per repository | deliberately near zero: the framework lives in the image, not a cache (the SDE build is 61 MB, cached only if we choose to) |
| Artifact storage | 500 MB (shared with Packages) | a few MB of logs, uploaded only on failure, default 90-day retention |
| Runner disk | ~14 GB | image layers + the SDE build (~2–3 GB) |
| Concurrent jobs | plan-dependent | 3 nightly jobs; irrelevant |

Two things to watch as the suite grows: the `full` job's wall-clock (180-minute
timeout today) and artifact retention, since a repeatedly-failing job uploads
logs every night.

## 2. The binding constraint is the build, not the minutes

Measured in the development checkout:

| Piece | Size | Notes |
|---|---|---|
| SerenityOS checkout | 205 MB | `libgui-wayland/scripts/fetch-serenity.sh`: blobless, sparse, **pinned** (`80baeb29…`) — reproducible and much smaller than a full clone |
| wlroots (vendored source) | 31 MB | `third_party/wlroots`, meson build |
| **Lagom framework build** | **1.2 GB** | LibGfx/LibGUI/LibWM + tools |
| SDE build | 61 MB | compositor, services, applets, apps, tests |

Dependencies + wlroots + Lagom + SDE, cold, is realistically **1–2.5 hours on a
4-vCPU runner**. Free minutes make that possible; it does not make it useful to do
on every push. Two mechanisms, in order of preference:

1. **A prebuilt image on ghcr.io** (`ci/Containerfile`): distro deps, wlroots, and
   the Lagom framework baked in, keyed on the SerenityOS pin. Jobs then build only
   the SDE and run tests. Public images are free.
2. **Actions cache** (10 GB per repo on Free): cache the framework build keyed on
   the SerenityOS pin. The framework does *not* depend on the test matrix — only
   the 61 MB SDE build does — so one cache entry serves every configuration.

`ENABLE_LAGOM_CCACHE` is currently `OFF`; turning it on with a capped cache helps
the first build either way.

## 3. Toolchain

The port builds `-std=c++26`; the development machine has **GCC 16.2.1** and
**CMake 4.4.4**. A current Ubuntu LTS default toolchain will not do, so the image
is **Arch-based** (`archlinux:base-devel`) — which also matches the packaging
target in [`13`](13-native-session-and-aur-packaging.md) and always carries a
current GCC/CMake. Jobs run *inside* that image
(`jobs.<id>.container.image`), so `ubuntu-latest` is only the VM host.

## 4. What runs where

| Job | Trigger | Runs | Target |
|---|---|---|---|
| `smoke` | push, pull request | build from the image + `run-all-tests.sh --tier fast` | < 15 min |
| `full` | nightly, `workflow_dispatch` | `run-all-tests.sh --tier full` (everything) | < 90 min |
| `budgets` | nightly (non-blocking at first) | `run-perf-test.sh`, `run-session-memory-test.sh` | visible, not gating |

Failures upload each test's log as an artifact. `budgets` is non-blocking on
purpose: the 240 Hz p99 assertion and the PSS limits are machine-sensitive, and a
shared runner will flake them. The `SDE_PERF_*` / `SDE_SESSION_*_LIMIT_KB` knobs
exist so CI can express a looser gate without weakening the local budget; once a
runner baseline is measured, tighten them and make the job blocking.

## 5. What cannot run on a hosted runner

- **`run-profiler-test.sh`** — needs `perf_event_open`, which the runner's
  container blocks (`perf_event_paranoid`). It must **SKIP** with a reason rather
  than fail. Tracked in the tier list until the test detects it itself.
- **Host services** — NetworkManager, a PipeWire daemon, a portal frontend, a
  camera. Those tests are `full` tier and must skip cleanly when the service is
  absent; the per-push gate must never depend on one.
- **No `/dev/dri`.** Fine: the suite is headless by design, and Xwayland binds its
  own socket under the test's runtime directory.
- **DRM/KMS, libinput, real GPU, input→photon latency** — the R6 items in
  [`08-compositor-gaps.md`](08-compositor-gaps.md), not coverable in CI.

## 6. Hermeticity — and an incident worth reading

Two things stop a test run from being hermetic, and both bit on day one. The
suite is only safe to run on a working machine *because* of what follows.

### 6.1 The session's services answer for the test's (`SDE_SESSION_DIR`)

`LibWM` **defers** to a process already listening on the session's portal path, so
a test run on a machine with a live session can be answered by *that* session's
services instead of the compositor the test started. This is the failure mode
that made `run-audio-test.sh` red until it isolated itself, and it made
`run-setting-test.sh` red for the same reason.

`run-all-tests.sh` now gives **every** test a private `SDE_SESSION_DIR`, which
fixed `run-setting-test.sh` and makes the suite hermetic in CI as well. Tests that
want their own path still set it and win.

### 6.2 Xwayland shares the machine, and the compositor did not survive it

**What happened.** The first full local run — on the machine hosting the live
session this was written on — killed that session. The compositor crashed with:

```
SIGSEGV
  libwlroots: wlr_xwayland_set_workareas+0x11c
  WindowServer: update_xwayland_workareas   ← arrange_layers ← layer_surface_commit
```

**Why.** An X server's sockets are **abstract** (`@/tmp/.X11-unix/X<n>`) and are
therefore shared with every other X server on the machine — no filesystem
namespace separates them. Each test compositor enabled Xwayland, and Xwayland's
display selection is a race over a global namespace: the session's X server was
on `:1` and a test's took `:1` too. The session's X server died; the compositor's
`xwayland_started` flag only recorded that it had been ready *once*, so the next
layer-surface commit called `wlr_xwayland_set_workareas()` on a dead Xwayland,
which dereferences the XWM connection wlroots had since dropped → SIGSEGV → the
session's supervisor restarted it.

**Two fixes, one product and one process.**

1. **The compositor survives a dead Xwayland.** `update_xwayland_workareas()`
   now checks `wlr_xwayland_get_xwm_connection()` before asking wlroots to report
   the workarea. Any X server going away — for any reason, in any deployment —
   can no longer take the compositor with it. This is the real bug; the test run
   only found it.
2. **A test's X server cannot be seen by the session's.** `run-all-tests.sh`
   exports `SDE_XWAYLAND=0`, so no test compositor starts an X server unless its
   test asks for one. The five tests that *do* exercise X11 re-exec themselves in
   `unshare -Urnm` — a **network** namespace (abstract sockets are namespaced
   there, not by the filesystem) plus a mount namespace carrying a private,
   correctly-owned `/tmp/.X11-unix` (Xwayland refuses one it does not own, and
   the host's is owned by root, which is an unmapped uid inside a user
   namespace). Where unprivileged namespaces are unavailable (some containers)
   they fall back to skipping while a session owns the display.

   Verified with a session live: the tests pass, the session's socket table is
   byte-for-byte unchanged during the run, and the session's compositor pid never
   moves.

### 6.3 Coverage: tiers decide *when*, not *whether*

No test is excluded from CI. 83 run on every push; the 5 X11 tests
(`xwayland`, `xwayland-exit`, `taskbar-grouping`, `active-window`, `selection`)
run in the nightly `full` job and, thanks to §6.2, locally too — which they never
were safely before. Swapping the other 83 to Xwayland-off removes no assertion:
nothing outside those 5 asserts anything about X, so the X server they used to
start was incidental, and it was what made runs non-hermetic.

One open finding, recorded rather than hidden: `run-taskbar-grouping-test.sh`
fails its **X11 `WM_CLASS`** assertion — the compositor logs
`X11 window 0 class='' instance=''` for an `xterm`, so the grouping input is
empty. That is not a namespace artefact (the X client and the compositor are in
the same namespace and the native checks all pass); it looks like a real gap in
how X11 windows reach the group logic.

## 7. The driver

```sh
scripts/run-all-tests.sh                     # the per-push tier
scripts/run-all-tests.sh --tier full         # everything
scripts/run-all-tests.sh --only 'run-*portal*' --timeout 600
scripts/run-all-tests.sh --list              # the selection, with tiers
```

It discovers `scripts/run-*-test.sh`, runs each with a timeout, records how long
it took, recognises `SKIP:` output, and prints a summary with the slowest tests
and the tail of each failure. Exit status is non-zero if anything failed or timed
out. Tiers come from a marker in the test's header:

```sh
# ci-tier: full
```

Unmarked tests are `fast`. Marking is **evidence-based**: the durations the driver
prints are what put a test in a tier, and `# ci-tier: full` is for tests that are
heavy, timing-sensitive, or need something a runner lacks. A test that cannot run
here should print `SKIP: <reason>` and exit 0 — the driver reports it as skipped,
not failed.

Safety: the driver never signals anything but the test it started. Each test owns
its isolation (its own `setsid` process group and runtime directory) and its
`trap … EXIT` cleanup runs when a timeout sends it SIGTERM, so a timed-out test
still takes its compositor down with it. Nothing matches processes by name or
command line — see the incident note in [`25-performance.md`](25-performance.md).

## 8. Deliberately not covered

- **Real hardware** (DRM/KMS, libinput, multi-GPU, colour, direct scanout) — R6's
  remaining items need a machine, not a runner.
- **Accessibility (R5)** and the wlroots-gated Xwayland items.
- **A per-renderer matrix.** `SDE_PERF_RENDERER=auto` and `SDE_RENDERER=gles2` are
  runnable headless, but GL on a runner means llvmpipe; the matrix is worth adding
  only once the image carries a GL stack.
