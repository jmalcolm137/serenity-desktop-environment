# XDG desktop menu

**Status:** implemented · **Related:** [`14-r4.4-config.md`](14-r4.4-config.md),
[`35-xdg-user-dirs.md`](35-xdg-user-dirs.md)

The Taskbar's system menu can be built either from the SerenityOS `.af`
application files (the default, "Serenity style") or from freedesktop
`.desktop` entries ("XDG style"). The choice is a compositor config setting:

```ini
# $XDG_CONFIG_HOME/sde/WindowServer.ini
[Taskbar]
XDGMenu=false   ; false (default) = Serenity .af menu, true = XDG .desktop menu
```

`XDGMenu` is part of the shared schema: the compositor validates it (rejecting
anything that is not a boolean — `true`/`false`, `yes`/`no`, `on`/`off`, `1`/`0`)
and prints it under `[Taskbar]` in `scripts/sde-config list`. The Taskbar reads
the same layered file (user file over `$SERENITY_RES_ROOT/../etc/WindowServer.ini`)
so `sde-config` and the Taskbar cannot disagree. The change takes effect when the
Taskbar starts, like the other Taskbar settings.

```sh
scripts/sde-config set Taskbar XDGMenu true
```

## Serenity style (default)

`main.cpp:build_system_menu` discovers the installed `.af` files through
`Desktop::AppFile::for_each`, groups them by their `Category` (including
`Games/Puzzles`-style subpaths) and shows the `SystemMenu.ini` category icons
with each app's own icon. This is the unmodified SerenityOS behaviour, and it is
still the default: existing sessions and tests see no change.

## XDG style

With `XDGMenu=true`, `XdgMenu.cpp` scans `$XDG_DATA_HOME/applications` and every
`$XDG_DATA_DIRS/applications` directory (first entry wins for a duplicate desktop
ID) and builds the same category submenus from the freedesktop main category:

| `.desktop` category | menu submenu |
| --- | --- |
| `Development` | Development |
| `Game` | Games |
| `Graphics` / `Demo` | Graphics |
| `Network` | Internet |
| `AudioVideo` / `Audio` / `Video` | Media |
| `Office` | Office |
| `Settings` | Settings |
| `System` / `Utility` (and anything else) | Utilities |

The submenu labels are the Serenity system menu's existing labels (with their
mnemonics), so the shipped `SystemMenu.ini` icons keep working for both styles.
Entries with `NoDisplay=true`, `Hidden=true`, a `NotShowIn` match, or a
non-`Application` `Type` are skipped; `OnlyShowIn` is honoured, so entries that
list neither `SDE` nor `Serenity` are hidden. `TryExec` is resolved (the Serenity
`/bin/...` path first, then `$PATH`) and an entry whose program is missing is
skipped.

Launching follows the desktop entry: the `Exec` line is parsed into argv with
quote/backslash handling and the `%f`/`%F`/`%u`/`%U`/`%d`/`%D`/`%n`/`%N`/`%i`/
`%c`/`%k`/`%v`/`%m` field codes dropped (`%%` is a literal `%`). `Terminal=true`
runs the command through Serenity's Terminal (`-e`). `Icon=` is loaded when it is
a path, a `resource://`/other URI, or a Serenity icon name under
`resource://icons/16x16`; otherwise the icon is derived from the executable, as
in the Serenity menu.

## The Serenity applications' entries

Serenity apps ship `.af` metadata, not `.desktop` files. The session therefore
generates freedesktop entries from them at login:

```sh
scripts/generate-desktop-entries.sh --output "$XDG_DATA_HOME/../sde/xdg-data"
```

The generator reads `Base/res/apps/*.af`, maps the Serenity category to a
freedesktop main category, strips `&` mnemonics from `Name`, and writes one
entry per app (skipping `ExcludeFromSystemMenu=true`) with `Type=Application`,
`Exec=/bin/<App>` (resolved by the port to the session app directory),
`TryExec=/bin/<App>`, the `.af` `Arguments`, and `OnlyShowIn=SDE;` +
`X-SerenityOS=true`. `sde-session.sh` regenerates the tree into
`$XDG_CONFIG_HOME/sde/xdg-data` before the compositor starts and prepends it to
`XDG_DATA_DIRS` (`SDE_XDG_DATA_UPDATE=0` disables the regeneration, for tests).
`install-sde.sh` also generates entries into `<prefix>/share/applications` and
exports `XDG_DATA_DIRS=<prefix>/share:…` from the `sde-session` launcher, so an
installed session works before the per-user tree exists.

The generated entries are deliberately machine-written and marked
`# Generated by sde-generate-desktop-entries; do not edit.`; a user can drop
hand-written entries into `$XDG_DATA_HOME/applications` (higher priority) to
override or extend them.

## Tests

`scripts/run-taskbar-xdg-menu-test.sh` starts the Taskbar headless twice:

1. `XDGMenu=true` with a generated data dir: the log must show the XDG menu was
   built, the entries discovered, and `Calculator` present;
2. the same data dir with `XDGMenu=false`: the log must show the Serenity `.af`
   menu was used;
3. the compositor's `sde-config` schema is covered by `scripts/run-config-test.sh`
   (default `XDGMenu=false`, `set`/`get`, and rejection of an invalid value) and
   the fuzz test.

Both runs use a private `XDG_RUNTIME_DIR` and `SDE_STATE_DIR`, so they never
touch a live session.

## Known gaps

- Only localized `Name`/`Comment` (`Name[xx]`, `Comment[xx]`) are not read; the
  unlocalized value is used.
- `Actions`, `MimeType` handlers, `Keywords`, and `StartupNotify` are ignored.
- `DBusActivatable=true` entries with no `Exec` are skipped (there is no D-Bus
  application-activation service yet).
- The icon lookup is SerenityOS's resource icon set plus executable-derived
  icons; a full XDG icon-theme search (hicolor, inherited themes) is still the
  compositor's/themed-icon work tracked in [`04-known-gaps.md`](04-known-gaps.md).
- The XDG menu is read once at Taskbar start; a newly installed entry needs a
  Taskbar restart (or `sde-session` restart), unlike the compositor config which
  live-reloads.
